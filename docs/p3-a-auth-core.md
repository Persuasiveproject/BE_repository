## 구현과 사용 경계

### 카카오 인증과 가입

`accounts.kakao.verify_access_token()`은 고정 HTTPS 카카오 API에서 토큰 정보와 프로필을 조회한다. 앱 ID, 양의 회원번호, 만료, 두 응답의 회원번호 일치를 검사한다. 리다이렉트를 따라가지 않으며 응답 크기·시간을 제한한다. 제공자 오류에는 토큰·시크릿·응답 원문을 넣지 않는다.

`verify_authorization_code()`는 설정한 Redirect URI만 허용해 서버에서 코드를 교환하고 동일한 토큰 검증을 수행한다. HTTP 호출 측은 OAuth state와 시작 요청의 결합을 검증해야 한다. 이 PR이 state·콜백 API를 구현한 것은 아니다.

`register_verified_identity(identity, agreements=...)`는 서버 검증 결과만 받아 신규 회원·보상 원장·약관을 하나의 트랜잭션으로 처리한다. 약관 실패 시 신규 회원과 보상을 모두 취소한다. 삭제 계정은 ACCOUNT_UNAVAILABLE로 거절하고 기존 회원에게 재지급하지 않는다. 이메일이 없으면 가짜 이메일을 만들지 않는다. 신규 가입의 이메일·닉네임 미제공 정책은 합의 필요다.

[카카오 공식 REST 문서](https://developers.kakao.com/docs/ko/kakaologin/rest-api)의 access_token_info와 user/me, 토큰 교환 계약을 기준으로 했다.

### 약관

`save_agreements(user_id=..., decisions={term_id: bool})`는 유효한 약관 존재, 필수 동의, 상태를 검사해 복합 PK로 저장한다. 게시된 필수 약관이 없으면 설정 오류로 막는다. 내부 서비스는 각 유형의 effective_at이 가장 최근인 약관을 현재 버전으로 취급한다. 현재 버전 판별 방식과 동의 변경 이벤트 보관은 HTTP 출시 전에 팀 검토가 필요하다. 배열 중복·빈 배열의 HTTP 정책은 결정하지 않았다.

### 세션

`SessionStore(redis_client, access_lifetime=...)`는 기존 Redis를 사용할 수 있는 내부 구현이며 새 테이블·외부 서비스를 만들지 않는다. 저장소 선택 자체는 아직 출시 계약이 아니다. 실행 중인 서비스에는 연결하지 않았다.

- 난수 access/refresh 토큰의 SHA-256 해시만 저장한다. 반환 객체 repr에서도 원문을 감춘다.
- 세션 절대 유효기간은 14일이다. access 유효기간은 호출자가 명시해야 한다.
- 갱신 시 `rotate_refresh=True/False`를 명시해야 한다. 어느 정책도 기본값으로 확정하지 않는다. 갱신은 14일 기간을 늘리지 않는다.
- Redis WATCH/MULTI로 같은 refresh 토큰의 동시 회전은 한 요청만 성공한다. 회전 시 이전 access 토큰도 무효화한다.
- access와 refresh 어느 쪽으로도 해당 세션만 폐기할 수 있다. 전달 방식과 로그아웃 HTTP 멱등 응답, 전체 기기 폐기는 결정하지 않는다.
- 삭제 회원은 인증 불가다. 제한 회원은 허용된 읽기 등을 위해 인증 가능하지만, 갱신은 현재 API #2의 ACTIVE 조건을 따른다. 이 정책 조합은 팀 검토 대상이다.
- 키는 `ye:auth:v1:` 접두사를 사용한다. Redis 오류를 인증 성공으로 처리하지 않는다. Redis 클라이언트 연결·ACL·장애의 HTTP 오류 매핑은 향후 API 연결 시 작업한다.

### 모의 본인 확인

`MOCK_IDENTITY_ENABLED=false`가 기본이다. 테스트 환경에서만 전용 proof 서명 키와 동일인 HMAC 해시 키를 설정한다. 같은 사람인지 판별하는 값은 원문을 DB에 저장하지 않는다.

시작 함수는 유효기간을 호출자가 지정하며 무작위 request_id를 만든다. 완료는 증명의 서명, 사용자·요청 결합, 현재 요청, 만료를 검사한다. 두 계정의 동시 완료는 DB의 verified_identity_hash_uniq로 한 계정만 성공한다. VERIFIED 행이 있는 계정의 재시작은 ALREADY_VERIFIED로 거절한다.

`issue_mock_proof()`는 신뢰하는 모의 제공자 측의 테스트용 함수다. 앱에 공개하거나 person_key를 그대로 받아 인증 완료시키는 경로를 만들면 안 된다. 실제 제공자, 보관·탈퇴 후 재가입 정책은 C파트와 합의해야 한다. `require_verified_identity()`는 아직 기존 API에 연결하지 않았다. 전용 오류 코드도 현재 HTTP 계약에 추가하지 않았다.

## 마이그레이션과 설정

- #73의 accounts.0004 다음 accounts.0005를 적용해야 한다.
- 기존 DB에 같은 해시로 VERIFIED인 계정이 여러 개 있으면 제약 추가가 실패한다. 데이터를 임의 삭제·병합하지 않는다.
- `KAKAO_APP_ID`, `KAKAO_REST_API_KEY`, `KAKAO_CLIENT_SECRET`, `KAKAO_REDIRECT_URIS`는 실제 연동 전에 서버에 설정한다.

## 검증 범위

### 기능 동작

로컬 실제 PostgreSQL 17·Redis 7.4에서 `python manage.py test -v 1` 전체 396개가 통과했다(124.259초). 신규 인증 서버 로직 테스트 30개와 #73 가입 보상 테스트 10개가 포함된다. 동시 토큰 회전과 두 계정의 동일인 동시 확인은 실제 Redis와 별도 PostgreSQL 연결로 검사했다. 테스트용 Redis 키는 실행별 고유 접두사로 격리하며 공유 DB 전체를 지우지 않는다.

카카오 HTTP 응답은 mock으로 제공했다. 원장 실패와 네트워크 오류는 예외 주입으로 검사했다. 기존 테스트 중 force_authenticate나 mock을 사용하는 검사는 그 우회 범위까지 검증한 것이다. 전체 테스트 출력의 결과 저장소 장애 경고는 기존 장애 주입 테스트에서 발생했고 테스트는 통과했다.

Django check, makemigrations --check --dry-run 및 git diff --check도 통과했다.

### API 명세 일치

HTTP URL·인증기·응답·오류 코드를 새로 추가하거나 변경하지 않았다. 따라서 이번 내부 서비스 테스트로 카카오 로그인 API 전체 적합성을 주장하지 않는다. 전체 API 명세의 필드·인증·오류 계약을 새로 전수 대조한 검증도 아니다. 보류 중인 정책은 위에 명시했으며, 임시 HTTP 계약으로 대체하지 않았다.

### 실제 연동

PostgreSQL·Redis 연동은 실제 실행했다. 카카오 서버 실호출·실제 본인 확인 제공자·앱 연동·AWS 배포는 미검증이다. 공개 인증 API와 본인 확인 권한의 기존 API 연결이 남아 있으므로 전체 로그인 완료 상태가 아니다.
